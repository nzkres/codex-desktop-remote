**2026-10-08最新增量：** Windows已用签名本地包维护安装alpha.6，用户确认手机原任务两条回复均显示；Android/relay仍alpha.5。此次维护交接没有走普通HTTPS OTA，故下一轮Windows的实际N/N+1改为**alpha.6→alpha.7**，之后再逐端Android和relay。alpha.7准备与待确认发布范围见[审查清单](WINDOWS-ALPHA7-OTA-REVIEW.md)和STATUS。下方alpha.5→alpha.6统一组合为历史初始计划，不应据此降级或重复首装。

2026-10-08最新授权与结果：用户已批准PR #1合并、专用测试签名，以及在现有服务器部署**独立隔离**的alpha.5 relay/FRPS/HTTPS/私有OTA。服务器内安装、鉴权、合成更新/回退、受管启停均通过；主电脑公网 `9443` HTTPS 鉴权下载及 `17443` FRPS 合成夹具亦通过。现用服务和身份未接管；真实身份迁移、手机安装和真实任务N→N+1不在本次授权范围。分层证据见[STATUS](../STATUS.md)与[隔离部署记录](OTA-ISOLATED-DEPLOYMENT-20261008.md)。

2026-10-08 制定。第一目标是一台 Windows 电脑、一部 Android 手机和一个隔离中继，能持续接续同一条 Codex Desktop 原生任务，并分别完成一次真实在线升级。先完成这个闭环，再分批修复 BUG；不扩大到多电脑、自动数据库迁移或新的任务执行器。

## 当前起点与完成标准

alpha.3 已交付更新程序、隔离测试和归档包，alpha.4 增加三端私有下载鉴权。alpha.5受控首装构件基于`1a4b4c0`：Windows/Linux CI和main受控Android CI均成功；Windows/WSL新临时home首装通过。隔离服务器Python3.12.3/systemd255/cgroupv2环境已完成alpha.5安装、合成0.0.2升级/坏候选回退及四棵自有树验收；主电脑公网完成三组件鉴权下载、TLS/RSA/大小/哈希核对与FRPS无任务夹具转发。真实手机/电脑首装和真实设备N→N+1尚未验收，不能以合成公网结果替代它们。

alpha.4保留为私有鉴权开发预览，普通debug APK信任为空。**当前Windows在线验收为已安装的alpha.6→alpha.7；Android/relay仍从alpha.5开始逐端准备下一版本。**原始alpha.5→alpha.6统一组合仅是历史计划。各端必须使用本机实际版本比较，Android versionCode递增。既有归档不换包；已签元数据过期时，以新序号重新签发相同已验证文件，不改包字节或关闭验证。以后可独立更新某个组件。

完成须同时满足：真实 HTTPS 下载、发布者及包校验、实际运行版本改变、身份/数据/权限保留、手机与 Desktop 同任务继续交互、失败行为可解释。没有执行的步骤记“待测”，下载成功、CI 成功与 `probe_verified` 均不能代替这些结果。

## 第一阶段：建立可重复的首装基线

1. test 渠道的隔离 HTTPS 源已安装并从主电脑公网验收，分别使用 `desktop-remote-updates/test/android/`、`windows/`、`relay/`；不覆盖旧 Android 更新接口。签名公钥/source 随首装固定，test/stable 分开；首轮不做渠道切换。
2. 准备 alpha.5 的三端受控构件。APK 使用固定证书并内置 test trust；Windows/relay 使用已签 ZIP、元数据和审核公钥建立新受管目录。签名、依赖和命令见 [发布](OTA-PUBLISH.md)与[安装](install/README.md)。
3. 新 relay 基线已在隔离服务器安装：独立账号/数据库、明确端口、HTTPS/FRPS、受管宿主、私有管理 socket、委派 cgroup v2；服务器内 stop/start、树清空、DB 摘要保持通过。公网合成 HTTPS/FRPS 链路已验收，后续仍须真实手机和 Desktop 任务验收，不能复制旧数据库来完成首装。
4. 在 Windows 新目录配置专用 Desktop 任务，核对精确版本/文件哈希和权限，再装手机基线并手动配对新设备。保留现用 APP、连接器和身份；相同包名的已装 debug APK 若签名冲突，先查实际证书和数据，不能默认卸载。必要时先用另一台测试手机。
5. 在 N 基线先完成“手机发送 → Desktop 同一任务接续 → 手机看到接续”。核对任务 UUID、设备绑定、权限摘要和三端实际运行版本；另测连接器 `/api/connector/update-status` 的新鲜 idle/权限/回执证据。旧接口、活动或未知任务必须阻止安装。

Windows 当前 ZIP 仍需要外部 Python/Tk/cryptography、固定 Node/FRP/Desktop。维护者可以完成首次受管安装供个人试用；若交付标准是“普通用户自己下载安装”，必须先补 Windows 安装入口与运行时打包/检测，并验证干净电脑首装。源码 ZIP 的 OTA 测通不能勾选“EXE 安装器已完成”。中继还须明确服务启动与重启方式；Desktop/CLI 继续作为外部依赖检测。

## 第二阶段：三端逐一完成 N→N+1

alpha.6 至少有一条能体验、能核对的版本说明，可仅作为受控 OTA 演练版本，不必为了升级测试添加新功能。先上传版本化包，独立核对服务端实际大小/哈希与签名，再原子发布对应 `latest.json`。每组件的序号递增；同版本不换包。发布过程记录源码、渠道、公钥/证书指纹、有效期和构件哈希。

| 次序 | 实际操作 | 通过条件 |
| --- | --- | --- |
| 1. Windows | 用户正常断开连接，窗口检查、阅读说明并触发安装；独立助手运行，新窗口打开后再连接 | GUI/适配器实际 N+1；原设备绑定、DPAPI 身份、任务与权限保留；事务 committed；同一 Desktop 任务手机→Desktop→手机再次通过 |
| 2. Android | APP 检查、下载、由系统确认覆盖安装；重开 APP | 同包名/同 APK 证书、实际 versionCode 和 APK 哈希匹配；账号、选定设备/任务及测试草稿保留；安装回执已核验且取得新鲜任务证据；同任务交互通过 |
| 3. Relay | 管理员在任务空闲后依次 check/stage/apply，等待维护和新服务健康 | 实际中继 N+1；账号、设备登记和配置保留；旧树退出与候选激活证据明确；重新连通并完成同任务交互 |

每次只升级一个组件，上一项验收完成后再开始下一项。记录组合，例如“手机 N、Windows N+1、中继 N”，避免一次全换后不知道哪个组件出问题。最后再重启三个原型并复测，确认固定入口选中已提交版本、身份与配置可持续使用。

中继 apply 切换服务后，原宿主仍保留自身进程代码和句柄；若本批修复宿主，须另做受控 stop/start 并核验宿主版本，不能只看服务版本。Python/Node/FRP 不是本版 OTA 自动更换项。Android 不承诺自动降级；坏包应阻止安装，已安装故障通过保留数据的新版本修复，或另行审查恢复。

## 第三阶段：失败演练与交付签收

破坏性用例只用独立测试源、测试身份和数据库。错误签名/坏包不得投放现用源；未知结果不得自动重试或重放任务。

| 场景 | 必须看到的行为 | 验证层级 |
| --- | --- | --- |
| 匿名、过期/撤销凭据、暂停设备、跨组件/跨源、重定向 | 元数据和包均拒绝；凭据不发送到其他 origin；账号变化后手机旧候选失效 | 自动测试 + 已部署隔离 HTTPS 源 |
| 错签名、坏包、错误平台/兼容档/渠道、过期、重放、同版本换包 | 拒绝安装，旧版与数据不变 | 自动测试 + 隔离测试源实际拒绝 |
| 下载断网/空间不足 | 明确失败，可重新准备下载；未切换运行版本 | 隔离网络/测试目录 |
| 任务活动、审批或回执未知 | 更新延期；原任务不被终止或重放 | 真实专用任务 + 合成歧义用例 |
| Android 取消系统安装 | 保留原版并提示待安装/可重试，不显示成功 | 测试手机 |
| Windows 助手独立、自然退出竞态、候选后代残留 | 助手不依赖旧 GUI；仅原始句柄/自有树；未证实清空不抢启回退 | 自动测试 + Windows 隔离安装 |
| Windows/relay 新版不健康 | 清理候选树、保护数据后才回退；若回退失败则 needs_review | 两版隔离安装 |
| 切换中进程退出/模拟断电 | 下次启动识别未完成事务；恢复成功或明确闭锁，不猜测恢复、不恢复旧 DB 覆盖新数据 | 隔离进程/虚拟机，不能直接关掉现用电脑或服务器电源 |

每条验收记录至少填写：日期、组件实际 N/N+1、渠道、源码提交/CI、构件哈希与签名标识、操作步骤、结果、事务阶段、身份/权限/数据核对结果、同任务交互结果、问题编号与验证人。只保存脱敏结果；私钥、token、DPAPI 文件、数据库和原始任务内容不进仓库。

交付时在 STATUS/WORKLOG 记录全部结果，并提供固定签名的首装包、在线候选、当前运行版本组合、部署清单、启动方式、恢复步骤、版本历史和未解决问题。**权限/数据错误、核心连接失败、不可诊断的更新失败属于阻断项**；不能宣称已完成并推入普通 BUG 批次。若只完成源码运行模式，明确标记“维护者首装”，不写“普通用户安装完成”。

## 验收后的 BUG 批次

沿用 [现有测试反馈](https://github.com/nzkres/codex-desktop-remote/issues/new?template=test-feedback.yml)，一个问题一条记录，写三个软件实际版本、系统/Desktop 版本、预期/实际、复现步骤、脱敏错误码与是否阻断任务；未知消息先核对原任务，不重复发送。

- **阻断问题**：身份/权限/数据风险、无法连接、无法完成/恢复 OTA；暂停后续放量，单独处理并复验。
- **普通功能 BUG**：每批 1–3 个相关问题，确定验收条件，修复与回归后只提高变化组件版本；发布一个新 test 构件，不覆盖旧包。
- **体验问题**：排到后续批次，保持复用 UI 和第一版范围；新功能单独列项，不能混进修 BUG 批次。

固定顺序：问题记录 → 小改动/测试 → 更新对应 releases.json 与仓库版本说明 → 测试渠道 OTA → 本次问题复现消失 + 同任务闭环与数据保全回归 → 记录实际运行组合。通过后才扩大使用；进入 stable 还须独立的信任配置和首装/渠道方案，不默认 test 安装自动变 stable。
